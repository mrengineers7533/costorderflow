
# Manufacturing → Requisition → Purchase Module (Base)

Goal: add a complete base workflow on top of the existing OA/BOQ system without changing any current calculation, pricing, approval, revision, or UI behavior. Everything resolves to the **latest approved BOQ per OA family** (using `COALESCE(parent_order_id, id)` as the family key, the same key already used in `boq_family_share_tokens` and `ApprovedBoqModule`).

---

## 1. What already exists (reused as-is)

- `boqs` with `verification_status='approved'`, `revision`, `is_current` per family — single source of truth.
- `boq_revisions` — full snapshots per revision (used for row-wise diff).
- `boq_remarks_audit_log` — per-row remark history.
- `boq_family_share_tokens` + `get_latest_approved_boq_by_family_token` RPC — stable link → latest approved.
- `src/lib/boq/pdfDistribution.ts` — enriched BOQ PDF (remarks, design comments, change log).
- `ApprovedBoqModule` (Purchase/Manufacturing list + detail shell).

No edits to any of these. New work plugs in on top.

---

## 2. New database objects (additive only)

New migration introduces:

**`requisitions`** — one per (boq family, revision) when generated by Manufacturing.
- `order_root_id`, `boq_id`, `boq_revision`, `requisition_number` (e.g. `REQ/26-27/0004-R1/001`)
- `status` (`draft` | `issued` | `in_purchase` | `closed`)
- `family_token` (FK to `boq_family_share_tokens.token` so Purchase link auto-resolves to latest)
- `pdf_path`, `share_token`, timestamps, `user_id`
- RLS: owner or admin.

**`requisition_items`** — one per Finish Good item on the BOQ at generation time.
- `requisition_id`, `boq_item_id`, `item_no`, `description`, `model_number`, `quantity`, `unit`, `remarks`
- `fg_snapshot` jsonb (frozen copy of BOQ row at generation)
- `purchase_status` (`pending` | `checked` | `lotted` | `ordered`)
- `lot_no` nullable, `purchase_category` (`steel` | `outside` | null)

**`fg_raw_material_map`** — placeholder for future RM mapping (Finish Good → Raw Materials). Empty for now.
- `model_number` (key), `raw_materials` jsonb (array of `{material, qty, unit}`)
- Admin-writable; everyone reads. No calculation logic yet.

**`requisition_raw_materials`** — placeholder rows generated per requisition_item using map (or empty rows when map missing).
- `requisition_item_id`, `material`, `required_qty`, `unit`, `source` (`mapped` | `manual` | `placeholder`)

**`requisition_lots`** — Purchase-side lot grouping.
- `requisition_id`, `lot_no`, `category` (`steel` | `outside`), `notes`

**`requisition_distribution_log`** — mirrors `boq_distribution_log` for audit (who sent which requisition to which Purchase emails).

**RPC `get_requisition_by_token(_token uuid)`** — SECURITY DEFINER, returns the requisition + items joined to the **latest approved BOQ revision** for that family so the public link is always revision-current.

**RPC `latest_approved_boq_for_family(_root uuid)`** — small helper used in views (already implicit; expose as function for reuse).

All tables: RLS enabled, owner-or-admin policies, identical pattern to existing tables.

## 4. Auto-revision behavior

- Manufacturing list and Purchase list already pick latest approved per family — unchanged.
- Requisition public link uses `get_requisition_by_token` which joins to the latest approved BOQ, so PDF re-renders against current data on open.
- When a new BOQ revision is approved, the requisition row gets a computed `is_stale` flag in the UI (compare `requisition.boq_revision` vs current latest). UI shows banner "BOQ revised to Rn — regenerate requisition" with a one-click **Regenerate** action that supersedes the old requisition (`status='closed'`, `superseded_by_id` link) and creates a new one for the new revision.
- No automatic email send; user action only (consistent with prior decision).

## 5. Row-wise history

Reuse the existing diff engine in `pdfDistribution.ts` (already does field-level diff using `boq_revisions` snapshots). Extract it into `src/lib/boq/revisionDiff.ts` (pure refactor, no behavior change) and consume from:
- Manufacturing detail row-history drawer
- Requisition PDF "Changes since previous revision" section
- BOQ distribution PDF (existing usage continues to work)

Columns tracked: Description, Model, Qty, Unit, Remarks, Rate, Amount, with previous vs updated values and price delta.

## 6. Edge function

**`supabase/functions/create-requisition/index.ts`**
- Auth-validated. Input: `{ boq_id }`.
- Resolves family root, confirms BOQ is current+approved, generates next requisition number, inserts `requisitions` + `requisition_items` (snapshot from BOQ line_items), seeds `requisition_raw_materials` from `fg_raw_material_map` if present (else placeholder rows), creates a share token, returns the row.
- PDF rendering stays client-side for now (same approach as BOQ distribution); email send remains stubbed until user enables email domain (per your earlier message).
